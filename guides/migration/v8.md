# Migrating to v8 and the 2026-10 Pinecone API

v8 moves the SDK to Pinecone API version `2026-10`, which adds replica autoscaling for dedicated
read capacity and reports indexes, collections, backups, and restore jobs that use features
`2026-10` can't represent. The `X-Pinecone-Api-Version` header is sent as `2026-10` on every
request.

For most code, the only change is the import path. Every v7.2.0 call keeps compiling, and nothing
deprecated in v7 is removed.

## Update the import path

```sh
go get github.com/pinecone-io/go-pinecone/v8/pinecone@latest
```

Then replace `go-pinecone/v7/` with `go-pinecone/v8/` in your imports:

```sh
grep -rl 'go-pinecone/v7/' --include='*.go' . | xargs sed -i '' 's#go-pinecone/v7/#go-pinecone/v8/#g'
```

On Linux, use `sed -i` without the empty `''`. Then run `go mod tidy` to drop the `/v7` requirement
from `go.mod`.

## What's new: replica autoscaling

Set `Scaling.Auto` on `ReadCapacityDedicatedConfig` to let Pinecone move the number of replicas per
shard between `MinReplicas` and `MaxReplicas`. It works on every create method and on
`ConfigureIndex`. See [Replica autoscaling](../index-management/indexes.md#replica-autoscaling).

New in v8, all additions:

- `ReadCapacityDedicatedConfig.Shards` and `ReadCapacityDedicated.Shards`
- `ReadCapacityScaling.Auto` and `ReadCapacityAutoScaling{MinReplicas, MaxReplicas}`
- `ReadCapacityDedicated.ScalingStrategy`, with `ReadCapacityScalingStrategyManual` and
  `ReadCapacityScalingStrategyAuto`
- `Client.ListIncompatibleIndexes` and `IncompatibleIndex`, for indexes that use a feature
  `2026-10` can't represent. Each entry's `MinimumAPIVersion` is the earliest generally available
  API version that can describe the index (every later one can too), and `PreviewAPIVersion` is the
  earliest early-access one; either is `nil` when there's no such version. `ListIndexes` leaves
  those indexes out, and `DescribeIndex` refuses them with the error code `FAILED_PRECONDITION` and
  the reason `RESOURCE_INCOMPATIBLE_WITH_API_VERSION`, and its `PineconeError.Details()` carries
  the same versions. See
  [List indexes](../index-management/indexes.md#list-indexes).
- The same for collections, backups, and restore jobs: `Client.ListIncompatibleCollections` and
  `IncompatibleCollection`, `BackupList.IncompatibleBackups` and `IncompatibleBackup`, and
  `RestoreJobList.IncompatibleRestoreJobs` and `IncompatibleRestoreJob`. See
  [Collections](../index-management/collections.md#list-collections) and
  [Backups](../index-management/backups.md#describe-list-and-delete-backups).
- `PineconeError.ErrorCode`, `PineconeError.Reason`, `PineconeError.Message`, and
  `PineconeError.Details()`, read from the API's error response. Branch on `ErrorCode`, and on
  `Reason` when the API sets one; `Code` is still the HTTP status and `Msg` is unchanged, apart from
  a `"reason"` key when the API sends one.
- `PineconeError.TypedDetails()`, which returns the documented `details` keys as typed fields in an
  `ErrorDetails`.
- Reason constants: `ReasonResourceIncompatibleWithAPIVersion`, for a resource that uses a feature
  `2026-10` can't represent, and `ReasonTooManyDocuments`, `ReasonRateLimitExceeded`, and
  `ReasonMonthlyLimitExceeded` for document requests. See
  [Request limits](../data-operations/documents.md#request-limits).
- `ModelInfo.Modalities`, the kinds of input a hosted model accepts (`"text"`, `"image"`, `"pdf"`),
  and `ListModelsParams.Modality`, which lists only the models that accept one of them. See
  [Hosted models](../inference/inference-api.md#hosted-models).
- `User.Accounts` and `UserAccount{Type, NameId}`: the accounts an admin API user can log in with,
  when the organization has an SSO connection. See [Users](../admin.md#users).

## Behavior changes

These don't change any signature, but code that relies on the old behavior may need an update.

### List calls can leave items out

An index that uses a feature `2026-10` can't represent isn't returned by `ListIndexes`; there's no
error. Code that counts or inventories indexes should also call `ListIncompatibleIndexes`.
`DescribeIndex`, `ConfigureIndex`, `CreateCollection`, and `CreateBackup` refuse such an index with
the error code `FAILED_PRECONDITION` and the reason `RESOURCE_INCOMPATIBLE_WITH_API_VERSION`.

The same goes for other resources. `ListCollections` leaves such a collection out (list it with
`ListIncompatibleCollections`). `ListBackups` and `ListRestoreJobs` move such an item from `Data`
to `IncompatibleBackups` or `IncompatibleRestoreJobs`, and it still counts toward `Limit`, so a
page can hold fewer than `Limit` items in `Data` while `Pagination` points to more.
`DescribeCollection`, `DescribeBackup`, `CreateIndexFromBackup`, and `DescribeRestoreJob` refuse
such an item with the same error code and reason.

### Describing an autoscaled index

For an autoscaled index, `ReadCapacity.Dedicated.Scaling.Manual` is nil and `Scaling.Auto` holds
the bounds. Code that reads `Scaling.Manual.Replicas` without a nil check panics on such an index,
including one created from the console or another SDK. Check `ScalingStrategy` (a pointer, nil when
the API reports no strategy), or `Scaling.Manual` for nil, first. The live number of replicas per
shard is in `Status.CurrentReplicas`.

`ReadCapacity.Dedicated.Scaling` is nil when the SDK doesn't recognize the strategy;
`ScalingStrategy` still reports its name.

### Shards moved out of the manual scaling block

`ReadCapacityManualScaling.Shards` is deprecated. Use `ReadCapacityDedicatedConfig.Shards` on
requests and `ReadCapacityDedicated.Shards` on responses. The old field still works:

- On requests, it's sent as `Shards` when `Shards` isn't set. When both are set, `Shards` wins and
  the deprecated value is ignored, so a scaling block copied from a describe response doesn't undo a
  shard change.
- When you describe a manually scaled index, it's still filled in.

### `ModelInfo.Modality` is deprecated

API version `2026-10` reports a list, `Modalities`, instead of a single `modality`. `Modality` is
deprecated and still works: the SDK fills it from `Modalities`, with `"text"` for a model that
accepts text, as earlier API versions report for a model that also accepts other input. For a
model that accepts several kinds of input but not text, `Modality` is nil.

```go
// v7
fmt.Println(*model.Modality)
// v8
if model.Modalities != nil {
	fmt.Println(*model.Modalities)
}
```

### An empty `Scaling.Manual` block is an error

`ConfigureIndex` with a `Scaling.Manual` block that sets neither `Replicas` nor `Shards` now
returns an error without calling the API. v7 sent `"manual": {}`. API version `2026-10` requires a
replica count with manual scaling, and sending 0 would pause the index. Set `Replicas`; to change
only the shard count, set `ReadCapacityDedicatedConfig.Shards`; to keep the current scaling, leave
`Scaling` out. The create methods return the incomplete read capacity error below for an empty
`Scaling.Manual` block, as in v7.

### Error text changes

Code should branch on `PineconeError.ErrorCode` and `Code` rather than on message text. If
yours matches text, these messages changed:

- Server messages in a `PineconeError` are no longer HTML-escaped. v7 printed `<`, `>`, and `&` as
  `\u003c`, `\u003e`, and `\u0026`, so `>=` in a server message appeared as `\u003e=`; v8 no
  longer escapes those characters. The JSON in `Msg` decodes to the same values as before.
- Errors the SDK returns before calling the API for options that API version `2026-07` dropped
  (`SourceCollection` and `Schema` on `CreateServerlessIndex`, `Schema` on `CreateBYOCIndex`, `Embed`
  on `ConfigureIndex`, and a pod-based `Deployment` on `CreateIndex` or `CreateIndexFromBackup`) now
  say "Pinecone API versions 2026-07 and later" instead of "Pinecone API version 2026-07".
- The error for an incomplete `ReadCapacity.Dedicated` from the create methods now reads "Dedicated
  read capacity must be configured with a node type, shards, and a scaling strategy (Scaling.Manual
  with Replicas, or Scaling.Auto)". v7 said "... with a node type, scaling strategy, and manual
  scaling configuration". From `ConfigureIndex` on an index with OnDemand read capacity, it now
  starts "the index uses OnDemand read capacity, so it has no current Dedicated settings to keep",
  then names the same three settings.
- The `ConfigureIndex` error for `PodType` or `Replicas` on an index that isn't pod-based now ends
  with "To change the read node replicas of a serverless or BYOC index, set
  ReadCapacity.Dedicated.Scaling".

### Server errors follow 2026-10

The API returns errors under the `2026-10` rules, as a `*PineconeError`. In particular, a read
capacity change made while another is still being applied, including the initial provisioning right
after create, fails with the error code `ABORTED` and HTTP status 409. Under `2026-07` the same case
returned a 403 status, so v7 code that checked for 403 here should check for `ABORTED` instead.
`RetryPolicy` doesn't retry it.
Branch on the error code rather than the message text, but note that `FORBIDDEN` on a read
capacity request has more than one cause (see
[Replica autoscaling](../index-management/indexes.md#replica-autoscaling)).
`PineconeError.ErrorCode` holds the API's error code, and `PineconeError.Code` the HTTP status.
This loop retries a read capacity change on `ABORTED` and stops on any other error:

```go
params := pinecone.ConfigureIndexParams{
	ReadCapacity: &pinecone.ReadCapacityParams{
		Dedicated: &pinecone.ReadCapacityDedicatedConfig{
			Scaling: &pinecone.ReadCapacityScaling{
				Auto: &pinecone.ReadCapacityAutoScaling{MinReplicas: 1, MaxReplicas: 3},
			},
		},
	},
}
for {
	_, err := pc.ConfigureIndex(ctx, "my-index", params)
	if err == nil {
		break
	}
	var pcErr *pinecone.PineconeError
	if !errors.As(err, &pcErr) || pcErr.ErrorCode != "ABORTED" {
		log.Fatalf("Failed to configure index: %v", err)
	}
	// Another read capacity change is still being applied. Try again once it settles.
	time.Sleep(time.Minute)
}
```
